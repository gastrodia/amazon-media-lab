Playwright 的成功率低 16.7 个百分点，未挽回 Fetch 的失败。两次退化均出现在新加坡站商品 B09DKPP92N 的第三、第四轮：HTTP 200，标题 Server Busy，页面包含 validateCaptcha 表单与 Continue shopping 按钮，未得到商品内容。没有操作验证入口。美国站 ASUS 和 Kindle 两种方法均为 4/4；新加坡站 Fetch 为 4/4，Playwright 为 2/4。

Playwright 耗时包含固定 2.5 秒的额外渲染等待与两次解析，不能把全部耗时差归因于浏览器本身。浏览器一次性启动、任务间隔、冷却、截图和文件写入不计入该中位数。

## 素材覆盖

- ASUS：Fetch 各轮提取到 29 张图片、12–16 个视频源；Playwright 原始与渲染页面均为 29 张图片、12 个视频源。视频源数量变化不等于完整视频总量变化。
- Kindle：Fetch 和 Playwright 原始响应均提取到 12 张图片、0 个视频源；Playwright 渲染后为 12 张图片、2 个视频源。
- 核查原始 HTML 后确认：Kindle 这两个 URL 原本就在 `video[data-src]` 中，四次 Fetch 响应也全部包含。该差异是现有解析器只读取 `video[src]` 造成的覆盖缺口，不是浏览器独占信息。本轮没有修改生产解析器或重新定义成功率。
- 新加坡磁贴：正常响应中，两种方法均为 6 张图片、2 个视频源。

## 实验控制与边界

固定三个既有商品，每个商品每种方法尝试四次。商品顺序轮换，方法先后交替；并发 1、间隔 4 秒、遇到验证页同方法同站点冷却 30 秒。每次尝试不重试。

Fetch 复用现有实现，不保留 Cookie；Playwright 1.64.1 使用 Google Chrome 155.0.8059.80 的默认 headless 请求头，每个站点建立一个匿名内存上下文，在本轮内复用会话但关闭 HTTP 缓存。没有使用个人浏览器资料、账号、付费 API、代理轮换、隐身补丁或验证码处理。

主指标是拿到匹配的商品页面并由共享解析器提取至少一个素材。它不代表所有变体、评论或完整文件下载。原始响应与渲染后 DOM 的提取单独记录。

这 24 次是三个固定商品在短时间内的重复测量，不能当作独立随机样本，也不能推算全站或 Vercel 的成功率。两种进程的实际公网出口未核验；请求头、会话、传输与渲染同时不同，无法单独归因于其中一项。只观察到本轮保留浏览器会话并未避免新加坡站的两次限制。

## 工程结论

这轮数据不支持将主采集直接替换成 Playwright。可优先补齐 Fetch 的通用懒加载视频属性提取；浏览器保留为后续针对实际动态页面的可选采集路径，是否在独立服务器环境改善成功率仍需另测。

本轮仅新增本地实验脚本、开发依赖和报告生成工具，未接入付费 API，未部署或改变线上采集方式。相关 13 项自动化检查与 TypeScript 检查通过。
